# Wild Deck World Engine 2.0 — Implementation roadmap

Status: planning baseline. Working branch: `feature/world-engine-v2`, based on `feature/diplomacy-v1`.
Date: 2026-10-29.

## Vision and scope

Build a deterministic, Earth-sized, multiscale fantasy world with geographically coherent terrain, high-quality local rendering, persistent material interactions, and eventually shared support for Wild Deck strategy, Aethelburg character simulation, and Substrata autonomous agents. First prove Wild Deck card/world interaction. Do not integrate other games or resume AI work in the current phases.

The existing `Planet`, `PlanetSurfaceGenerator`, `PlanetAtlasServer`, `PlanetAtlasExporter`, and `WorldSimulation` are the starting point. The existing `planet-surface-v1` output and fingerprint must not change. Do not introduce a third match engine, modify production, incur costs, or change the paid database.

## Engineering invariants

1. Initial terrain is a pure function of signed 64-bit seed, explicit generator version, planet parameters, and coordinates. Sampling order, rendering detail, and threading do not change the world.
2. The planet is continuous across longitude seams, poles, region boundaries, and all levels of detail.
3. World modifications are stored separately from initial generation, replayable and persistent.
4. One authoritative Java simulation determines materials, capabilities, costs, legality, events, and outcomes. Renderers never own gameplay truth.
5. Actions cannot fabricate matter, energy, equipment, knowledge, or currency without explicit rules and sources.
6. The same object and physical rules apply whether introduced by a card or generated by the environment.
7. Kingdom-level and character-level representations must eventually reconcile, not duplicate or contradict state.
8. World knowledge is actor-specific; the omniscient atlas is a developer tool only.

## Release gates

Every milestone needs (a) source and regression tests, (b) new positive, negative and edge-case tests, (c) deterministic replay checks where state changes, (d) a reproducible demonstration, (e) measured performance for potentially expensive generation, and (f) an updated development log. CI green is necessary but not sufficient for visual/gameplay claims.

### M0 — Establish baseline and protect v1

- Capture the current branch SHA, generator version/fingerprint, documented reference seeds, existing test inventory and CI status.
- Add no behavioral changes.
- Acceptance: all existing tests pass in CI; v1 reference fingerprint unchanged; no deployment or billing changes.
- Tests: existing Maven Java tests, Node browser scripts, atlas Chromium checks and world sandbox demo where supported.
- Exit artifact: baseline report with exact command, SHA, counts, limitations and evidence.

### M1 — Versioned multiscale generator

- Add a v2 generator interface and coordinate/region identifiers without replacing v1.
- Deterministic derived seed channels for every independent generation layer.
- Define hierarchy for planetary fields, regional terrain and local mesh sampling; do not assume atlas pixels are world cells.
- Acceptance: sample same point in arbitrary order/resolution and receive equivalent authoritative values; adjacent region boundaries agree.
- Tests: seed repeatability, distinct/high-bit/negative seeds, version identity, poles/seams, precision, deterministic multithread sampling, order independence, LOD boundary equality, invalid coordinates, v1 regression fingerprint.
- Deliverable: API, tests, atlas selectable v1/v2 only after compatibility is proven.

### M2 — Coherent geography and hydrology foundations

- Add geological provinces, mountain-chain guidance, drainage, erosion-inspired shaping and broad climate suitability.
- Prefer bounded, explainable approximations over computationally expensive planet-scale fluid simulations.
- Acceptance: plausible continuous relief, no invalid elevations, drainage consistency and coherent regional patterns.
- Tests: finite bounds, reproducibility, seams/poles, drainage monotonicity or explicit lake basins, no unintended sinks, area-weighted statistics, terrain continuity, benchmark representative seeds.
- Deliverable: atlas geology/elevation/drainage overlays and documented statistical validation.

### M3 — Local high-resolution terrain

- Generate smooth mesh tiles on demand from authoritative fields, with adaptive LOD, stitching and camera-relative precision.
- Add local surface material masks, rock and soil placement; preserve world coordinates.
- Acceptance: zoom from atlas to representative local terrain without changing underlying landform; no visible tile cracks in reference scenes.
- Tests: tile-edge geometry agreement, LOD transitions, bounds, collision-to-height agreement, stable object placement, memory/time budgets, browser screenshot comparisons.
- Deliverable: standalone 3D inspection prototype, not a full game client.

### M4 — Materials and finite deposits

- Define reusable material properties, quantities, physical containers and source/sink accounting.
- Turn resource potential into deterministic local finite deposits; never treat 0–100 potential as inventory.
- Acceptance: objects have measurable state; extraction depletes stock; depletion survives regeneration.
- Tests: conservation, capacity limits, no negative stock, repeatable placement, failed-operation immutability, ownership and reach validation, edge-case numeric limits.
- Deliverable: sample region with inspectable, mineable deposits.

### M5 — Interactions and environmental responses

- Connect local generated objects to the existing `WorldSimulation` rules; extend incrementally to heat, water, excavation and obstruction.
- Ensure action outcomes are property-based, not card-name recipes.
- Acceptance: at least three different valid action chains yield meaningful distinct consequences and counters.
- Tests: valid/invalid attempts, resource and heat costs, no phantom state mutations, timing, spread/range bounds, wetness and fuel depletion, event determinism, response windows.
- Deliverable: interactive environment lab with event history.

### M6 — Persistence and replay

- Store seed, version, modified regions, object identity, material quantities, events and checkpoints; add explicit schema versions.
- Acceptance: unload/reload and restart preserve the same world; corrupted saves fail safely.
- Tests: round-trip snapshots, replay equivalence, concurrent edits, schema validation, wrong version/seed, truncation/corruption, identity collisions, deterministic state hashes.
- Deliverable: repeatable save/restart demo without requiring a paid database.

### M7 — Wild Deck card-to-world integration

- Choose one authoritative match path; connect card capabilities and world actions through validated commands, not direct renderer mutations.
- Preserve card ownership, hidden information, costs, movement, turns and diplomacy constraints.
- Acceptance: one complete small scenario supports several creative solutions with consistent world consequences.
- Tests: ownership/knowledge, capabilities, location and reach, cost, hostile action limits, invalid action immutability, multiplayer redaction, deterministic event replay, regression of existing match rules.
- Deliverable: playable Wild Deck vertical slice.

### M8 — Quality, performance and gameplay validation

- Improve rendering with biome-aware instancing, physically based surfaces, lighting and weather visuals; profile streaming and memory.
- Acceptance: benchmarked representative scenes, no major LOD popping or cracks, meaningful player choices confirmed through playtests.
- Tests: automated visual captures, camera fly-throughs, long-session memory, frame-time and generation latency benchmarks, restart tests, recorded human playtest feedback.
- Deliverable: demonstrable vertical slice and prioritized visual-quality backlog.

### M9 — Future multi-mode integration (deferred)

- Define adapters for Aethelburg bodies/actions and Substrata orders, learning NPCs and colony decisions.
- No code merge until M7 is stable.
- Acceptance: one shared entity can be affected consistently by a card, a character action and an NPC order.
- Tests: cross-scale reconciliation, event ordering, conservation, command authorization, state persistence and replay.

## First implementation sprint

1. Read actual v1 generator, planet, atlas, world simulation and their tests.
2. Run or inspect the current CI baseline and record exact evidence.
3. Implement M1 minimal v2 interface and deterministic coordinate/seed hierarchy without changing v1.
4. Add targeted tests before enabling any v2 atlas toggle.
5. Update `docs/LIVE_DEVELOPMENT_LOG.md` with observed results, not anticipated results.

## Definition of done

No milestone is marked complete from code compilation alone. Record exact commit, test command, CI link, measured outputs, known limits and next dependency. A beautiful renderer without persistent world interactions is a viewer; a simulation without tested card/world interactions is not yet Wild Deck.
